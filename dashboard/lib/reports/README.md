# lib/reports: Reporting Suite

Cross-client report builder for internal staff (admin and agency roles on an internal email domain; never the client role). Design: `11_reporting_suite_design.md` in the orchestrator scratchpad. This file records module boundaries and which package owns which file.

## Request path

```
POST /api/reports/query
  reportsAccessOrNull()          404 if null           (WP3, lib/authz.ts)
  ReportQueryRequest.parse()     400 invalid           (RS0, types.ts)
  getReportClients()                                   (WP3, clients.ts)
  resolveWidget()                413 too_large         (WP1, resolve.ts)
  compileWidget()                                      (WP2, compile.ts)
  runCached()                    422 / 504 / 500       (WP2, run.ts)
  getBenchmarks()  -> matchBenchmarks()                (WP3 benchmarks.ts, WP1 benchmarkMatch.ts)
  evaluateWidget() -> WidgetResult                     (WP1, evaluate.ts)
```

Every signature and intermediate type on this path is declared in `contracts.ts`. Implement against it (`export const resolveWidget: ResolveWidget = ...`) and do not change a contract file in your own package: ask the orchestrator.

Rules that hold everywhere:
- No data is not zero. A value that cannot be computed is `null` and renders as `NO_VALUE` (`"n/a"`, `lib/format.ts`) with the cell status as the reason. The design text's "em-dash glyph" means `n/a`.
- Partial sums are gaps (review F1, narrowed in semantic version 4). The compiled query returns, per bucket, a count of NULL rows next to every component sum. A gap is only missing spend: `paid_spend`, `meta_spend` and `google_spend` count their own NULL days, ad outcomes (`missingWhenNull`) count the days whose platform spend is NULL, and a NULL outcome on a day with spend is zero. A client bucket or total with such a day makes every gap term over it `no_data` ("Missing days"); COGS NULL on a revenue day is `not_measured`. `nullMeans: "zero"` components (shop columns, phase 2 campaign marts) and `nullAs: "zero"` terms (fulfilment and paid spend inside CM3) are not gaps. Combined and vertical rollups leave out a client whose own cell is a gap, `fx_missing`, `not_measured` or not connected, sum the rest and report `coverage`, `excluded` (name and reason) and `pointCoverage`; comparisons sum the same client set or are n/a.
- No user text reaches SQL. Identifiers come from the registry only; user values travel as typed params.
- Metric formulas are evaluated in TypeScript from summed components, never averaged.
- Reports never call `resolveClient()`; they use `getReportClients()`.
- Default display currency is CZK. Manami VAT is flagged with the `revenue_incl_vat` caveat, not recalculated. CM3 is the mart definition: `mart_daily_kpis.cm3` = revenue - COGS - fulfillment_cost - paid_spend (fulfilment and paid spend coalesced to 0), so the registry needs a `kpis.fulfillment_cost` component (design 2.3 omits it). On top, CM3 and CM1 % subtract the per-order costs stated in Settings, like Snapshot (semantic version 6): components `kpis.fulfilment_stated` and `kpis.other_cm1_stated` sum `orders` as money (native rows and per-month FX), and `evaluate.ts` multiplies each client's sum by `ReportClient.costRates` (`perClientRate`). The query route reads the rates from Postgres per request (`listClientSettings`), only for widgets that need them, and merges them into the clients after compile: they never reach SQL or a cache key. Unstated is 0, as on Snapshot.
- Shared queries (semantic version 6): the `kpis` mart is `selectAll`, so the compiler selects every KPI component whatever the widget asks for. Widgets with the same clients, period, grain and currency compile to byte-identical SQL and share the run.ts in-flight dedupe and cache entry; `CompiledQuery.components` is the superset and evaluation reads only each metric's components.
- Since migration 228 (deployed 2026-10-05) WooCommerce fee lines are netted and Woo COGS is NULL, not 0, when no costed line exists. `woo_fees_not_netted` no longer applies; a NULL COGS sum on positive revenue is `not_measured`, like a 0.
- Several marts per widget: `kpis` (`mart_daily_kpis`), `meta_campaign` (`mart_meta_campaign_perf`) and `meta_ad` (`mart_meta_ad_perf`). One CTE per mart, each with its own date predicate, guards, NULL counts and FX joins, `FULL OUTER JOIN USING (client_id, period, bucket)`. The evaluator keeps FX and foreign-currency guards per mart. Meta mart money is in the ad account currency (`currency` per row), converted per row and month like the KPI view; those marts are `accountCurrency`, so an ad account in another currency than the shop (an EUR shop with a CZK account) raises no "another currency" caveat. A day without Meta rows is absent from these marts (no data, never 0). Hook rate is 3-second plays (`video_views`) and hold rate ThruPlays, both over impressions of video ads (`meta_ad.video_impressions`). A video ad is decided per ad over the whole period (`filterScope: { key: "ad_id" }`: a pre-CTE `meta_ad__scope_video_play_actions_ad_id` with LOGICAL_OR(video_play_actions > 0) per client, period and ad, same date predicate and period tagging, asserted by `assertDatePredicates`), and all its days count, as on the Paid Meta tab.
- Entity marts (semantic version 7, HR3): `ad_launch` (`mart.rpt_ad_launch`, one row per Meta ad, lifetime to date, dated by first delivery) is `entity: { key: "ad_id", classifier: "creative_hit", exclude: ["is_preexisting", "is_relaunch"] }`. The compiler groups by the entity key too, selects every input component with ANY_VALUE whatever the metric, filters the `exclude` columns in WHERE and never emits a `classified` component. `evaluate.ts` (`classifyEntityRows`) turns each row into 0/1 counts (`launched`, `winners`, `open`) with `launchStatus()` from `lib/creative/hitRate.ts` and the client's `ReportClient.creativeThresholds`, which the query route reads from Postgres `creative_settings` per request and merges after compile, like `costRates`: SQL and cache key do not change when a threshold does. After that the counts are ordinary components. A client without thresholds is `not_measured` "No thresholds" for metrics that need them (rollups leave it out with coverage). A current period with open launches gets the `cohort_maturing` caveat, and lower-bound metrics (hit rate, winners) drop their delta when only the current period is maturing. In a widget that mixes an entity mart with another mart, every CTE carries `entity_key` ('' outside the entity mart) and the join is `USING (client_id, period, bucket, entity_key)`, so entity rows never duplicate another mart's sums. A metric may carry a fixed `reference` ({ value, label }): Line and Bar draw it dashed, KPI names it on hover.
- Cohort retention (semantic version 8, WR5): `customer_entry` (`mart.rpt_customer_entry`, one row per client and customer, dated by the first order date, so a period is an acquisition cohort) is a plain sum mart with `selectAll` and `rowFilter: { excludeTrue: ["is_early"] }`: every CTE of the mart gets `AND t.is_early IS NOT TRUE`, and `assertDatePredicates` requires it next to the date predicate. Its per-customer verdicts are INT64 0/1 columns summed like any count; `classes_configured` is BOOL and is a `bool` component (`COUNTIF(column)`); `is_early` is never a component. The seven metrics (`repeat_rate_90/180/365`, `third_order_rate_180`, `discovery_upgrade_90/180`, `discovery_entry_share`) carry `cohort: { population, minN: 30, lowN: 100, needsClasses? }`, applied in `evaluate.ts` on the summed counts of every cell: no product classes (sum of `classes_configured` 0) is `not_measured` "Products not classified" per client (rollups leave it out with coverage); a zero denominator with a population is "Not mature yet"; a denominator under 30 is "Too few customers"; under 100 adds the `low_n` series caveat; a population above the denominator adds `cohort_partial`. The two n rules run on the pooled counts only, never on one member of a rollup, so small clients are pooled. Caveats are per series: in a widget with two cohort metrics, a caveat earned by one shows on both hovers.
- No em dash anywhere (`npm run check:reports` enforces it for this folder).

## Notes for implementers

- **Charts.** `recharts` stays on 2.15.x: the Paid redesign (`components/paid/overview/SpendEfficiencyChart.tsx`) already imports it, so the design's "bump to ^3 costs nothing" no longer holds. Load chart widgets with `next/dynamic` either way.
- **Grid.** `react-grid-layout` is on the 2.x line (TypeScript rewrite, ships its own types, React 18+). Its `useContainerWidth()` returns a `RefObject<HTMLDivElement | null>`, which `@types/react` 18 does not accept as a `ref` prop; cast it (`containerRef as React.RefObject<HTMLDivElement>`) or measure with your own ResizeObserver. CSS: `react-grid-layout/css/styles.css`. The v1 API is available at `react-grid-layout/legacy` if needed.
- **Conformance.** Where a module is integrated (the route, or a check script), assert the whole module: `import * as m from "@/lib/reports/resolve"; const _c: ResolveModule = m;`.
- **Phase 2 metrics.** To ship one, move its id from `PHASE2_METRIC_IDS` to the end of `METRIC_IDS` in the same change that adds its mart to the compiler.
